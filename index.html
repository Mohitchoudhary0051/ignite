Privacy & security boundaries
Current implementation

What happens in this build

  • In nearby-network mode, file bytes move peer-to-peer through a DTLS-encrypted WebRTC data channel. The signaling server relays pairing details and ICE/SDP metadata, not file bytes.
  • The local server keeps each pairing room in memory until the selected 10-minute, 1-hour, or 24-hour expiry; it does not write file content or session records to disk.
  • Clear session closes the connection and clears this page’s held file data. It cannot delete copies you saved, screenshots, or OS/browser caches.

Connection limits

  • Pairing uses this local signaling server. Direct WebRTC is encrypted, but signaling can see the pairing code and connection metadata. No STUN/TURN relay is configured; blocked networks may fail.
  • The app needs a secure browser origin for phone camera scanning and cryptographic hash checks. Use localhost on this computer or a trusted HTTPS setup; do not bypass browser certificate warnings.

What a real optical transfer would mean

  • Air-gap optical transfer is not implemented in this build. A future mode must encrypt payloads before encoding them because anyone viewing the screen could capture the frames.
  • Expiry or revoke can end a live handoff; neither can claw back a copy already saved by the recipient.

Before production

Use cryptographically random session credentials, verify both peers, limit file size and session lifetime, verify a file hash, and document exactly what cleanup can remove.

FIRST RELEASE
